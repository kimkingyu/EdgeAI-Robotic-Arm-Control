### 📍 阶段 1：端侧 NPU 模型量化与推理加速专项【速度实测完成，但 INT8 检测不可用 ⚠️】
> **核心目标**：彻底压榨 RK3588 6 TOPS NPU 算力，量化压缩视觉模型并实现高吞吐并发推理。  
> **全部数据均由板端真实跑出**，详见 [`docs/benchmarks/NPU_BENCHMARK_REPORT.md`](benchmarks/NPU_BENCHMARK_REPORT.md)。
>
> ⚠️ **本阶段结论需要重大更正（在阶段 4 实现后处理解码时才发现）**：
> 下面的压缩率、算子直通率、时延与吞吐数据本身都准确，但 **INT8 模型的分类分支
> 在量化后恒为 0，检测功能实际不可用** —— 坐标算得出来，却永远不知道框里是什么。
> 一直没被发现，是因为后处理长期是空壳（`return []`），从来没人看过输出内容。
> 所以本阶段真正验证的是**推理速度与算子调度**，不是**检测可用性**。
> 修正方案与根因见 4.3.2。

- [x] **1.1 板端原生工具链搭建（推翻双机方案）**：
  - 探测发现 `rknn-toolkit2` 自 2.x 起已提供 **aarch64 原生 wheel**，遂放弃"x86 PC 转换 → 板端部署"的双机流程，改为**香橙派自转自跑单机闭环**；
  - 板端安装 `rknn-toolkit2 2.3.2`（含 torch 2.2.0 / onnx 1.16.1，`onnxoptimizer` 现场编译 aarch64 wheel）；
  - 推理运行时 `librknnrt.so` 由 **0.9.6 (2023) 升级至 2.3.2 (2025)**，旧版备份为 `librknnrt.so.bak_0.9.6`。
- [x] **1.2 INT8 训练后量化 (PTQ) 导出**（压缩达成，但**产出模型检测不可用**）：
  - 构建 COCO128 真实场景 100 张校准集（`data/calibration/`）；
  - 逐通道非对称 INT8 量化，**YOLOv8n: 12.2MB → 4.73MB（压缩 61.2%）**，YOLOv11n: 10.4MB → 4.54MB；
  - 攻克三处硬伤：`opset 20/22 超出 RKNN 上限 19`、`校准集路径二次拼接导致解码失败`、`YOLOv11 动态形状无法量化`；
  - ⚠️ **但分类分支已被量化破坏**：YOLOv8 输出头把坐标（0~640）与类别分数（0~1）拼在
    同一个 84 通道张量，共享量化参数时 scale≈2.51 —— 单个量化步长已大于分数最大值 0.93，
    分数必然归零。这是**数学必然而非精度损失**，`normal`/`mmse`/`kl_divergence` 三种算法
    实测全部如此。当时只核对了体积与算子直通率，没有验证输出数值，因此未能发现。
- [x] **1.3 算子硬件亲和力实测（结论与预期相反）**：
  - 逐算子解析构建日志 `Target` 列，**YOLOv8n 直通率 97.46%（115/118）**，**YOLOv11n 98.75%（158/160）**；
  - 二者纯计算算子均 **100% NPU 执行、零真实回退**，`Conv+SiLU` 被融合为 `ConvExSwish` 单算子；
  - v11 的 C3k2 + PSA 注意力在 RKNPU 2.3.2 上已被完整支持，直通率反优于 v8；但算子数多 35.6%（160 vs 118），**端到端耗时高 17.2%**，故仍选定 **YOLOv8n 为实时伺服主干**。
- [x] **1.4 系统级调频优化**：
  - 定位瓶颈：NPU 全程满频 1GHz、温度仅 46℃，真正卡点是 **CPU 侧的输入拷贝与输出反量化**被 `ondemand` 压在 1.2GHz；
  - 交付 `scripts/set_performance.sh`（CPU/GPU/NPU/DDR 全线锁频 + 大核绑定）；
  - 实测收益：单帧 **29.60ms → 23.23ms（-21.5%）**，P99 抖动 **±5.94ms → ±0.65ms（-89%）**。
- [x] **1.5 三核真并发推理池（关键突破）**：
  - 实测证伪"`core_mask=NPU_CORE_0_1_2` 即可多核加速"，因 `inference()` 同步阻塞，单实例三核仅 **1.03x**；
  - 重构 `src/inference/rknn_engine.py`，新增 `RKNNParallelVisionPool`：**每核心独立 RKNNLite 实例 + 多线程任务队列**；
  - 实测 **3 路并发 2.71x 近线性加速（38.5 → 104.5 FPS）**，单路时延仅增 7%；生产封装实跑 **112.99 FPS**。

**阶段成果**：单路实时检测 **44.24 FPS / 22.61ms**，系统峰值吞吐 **112.99 FPS**（可支撑 3 路工业相机），P99 抖动 ±0.65ms 满足伺服控制确定性要求。

> ⚠️ 以上吞吐数字全部由 **INT8 模型**跑出，而该模型的分类输出恒为 0。
> 速度是真实的，但**不可用的速度不构成性能成果**。当前实际在用的 FP16 模型单实例
> 为 **10.1 FPS（P50 99.24ms）**，比 INT8 慢 2.3 倍；FP16 的并发池吞吐尚未实测。

- [x] **1.6 量化精度验证【已完成，结论为负 ⚠️】**：
  - 原计划"相机到货后用真实工件数据集验证 mAP"，实际上**根本不需要等相机** ——
    用现成校准图片比对 ONNX 与 RKNN 的原始输出就能发现问题，而且这个检查
    在 1.2 当时就应该做；
  - 实测：同一张图 ONNX 原模型最高分 0.7996、20 个 anchor 超阈值；INT8 RKNN 分数
    全部为 0.0000。FP16 为 0.7998/20，与 ONNX 吻合；
  - **未做**：mAP@0.5 量化精度损失仍未量化 —— 需要标注数据集，且当前 INT8 已不可用，
    等修好输出头再测才有意义。

- [ ] **1.7 待办：恢复 INT8 可用性与 DMA-BUF 零拷贝**：
  - 拆分输出头让坐标与分数分两个张量各自独立量化，以取回 INT8 的速度；
  - 验证 `rknn-toolkit2 2.3.2` 是否支持逐层混合精度（让分类分支保持 FP16）；
  - 复测 FP16 在三核并发池下的吞吐，替换上面基于 INT8 的数字；
  - 接入 Linux DMA-BUF 内存共享通道，消除 CPU 侧图像搬运开销。

### 📍 阶段 5：MLIR 视觉预处理编译优化【编译器 MVP 完成，未取得加速 ⚠️】

> **核心目标**：自建 MLIR 编译器把 resize+BGR→RGB 编译成板端 AOT 算子，验证
> 能否在 RK3588 CPU 上超过 OpenCV。
>
> **实际结论：没有超过。** 满频条件下最优 MLIR 配置仍慢 4.38 倍，计划设定的
> "至少改善 10%" 门槛未达成。按两档验收，达到的是 **A 档「编译器工程 MVP」**，
> 而非 B 档「板端优化取得收益」。**OpenCV 保持默认后端。**

- [x] **5.7 未获收益的原因定位【已完成 ✅，结论与预设假设相反】**：
  - 板端未装 perf 且 `apt` 需交互式 sudo，改用 `perf_event_open` 直接读 ARMv8 PMU
    （`paranoid=2` 下测自身进程，无需 root），自写 `compiler/tests/pmu_counters.c`；
  - **踩坑**：一次打开 12 个事件时缩放比仅 0.38–0.45（6 个硬件槽位被复用），
    `branch_instructions` 读不到。分 4 组依次打开后缩放比全为 1.0，只采信这批数据；
  - **结论：瓶颈是指令数，不是访存**。MLIR 每输出字节 82.4 条指令，OpenCV 仅 11.6 条（7.1 倍）；
    但 MLIR 的 IPC **更高**（2.33 vs 1.79）、后端停顿**更低**（0.20 vs 0.41）、L1D 缺失率也更低，
    LL 缺失只差 1.29 倍而周期差 5.45 倍 —— 生成代码执行效率不差，是工作量本身多 7 倍；
  - 这解释了分块与向量化为何都无法翻盘：它们优化访存局部性与并行度，而瓶颈在指令总量，
    `tile_4x32_vector` 指令数甚至略高于未分块版；
  - **未做**：分支事件在本 PMU 上不可用（0x0D 恒读 0），分支开销未量化也不能声称排除。

- [x] **5.8 指令级归因：定位那 7.1 倍指令的来源【已完成 ✅】**：
  - 最内层循环 `.LBB0_7` 共 74 条指令却只产出 **1 个输出字节**（与 PMU 实测 82.4 条/字节吻合）；
  - **来源一**：融合后的 `linalg.generic` 是三维全 parallel，整套源坐标与权重计算留在最内层
    region，对每个 (行,列,通道) 都重算 —— x/y 方向各冗余 **1920 倍**，通道维再重复 3 倍，
    坐标与 clamp 相关指令占内层 41.9%。但即便完全提出循环外，估算也只降到 47.9 条/字节，
    **仍慢 4.13 倍**，所以这只解释了一部分；
  - **来源二**：向量化版本的 **1536 条 `ld1` 全是单字节插入通道**（`ld1 {v0.b}[i]`），
    无一条连续向量加载 —— `vector.gather` 让每个源像素单独加载再插通道，凑满 128 位向量需 16 条，
    而 OpenCV 一条 `ld1 {v0.16b}` 即可。SIMD 只用在乘加（384 条 `mla`），加载侧零收益；
  - **参照系说明**：板端 OpenCV 以 NEON 为 baseline 编译，对比对象是手工优化的向量化实现；
  - **结论**：要追上需让源地址计算走 affine 可分析形式、并让向量化产生连续 `ld1` 而非 gather，
    两者都是重新设计算子表达方式而非参数调优。收益与工作量需另行评估。
